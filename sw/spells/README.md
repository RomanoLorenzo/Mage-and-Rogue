# Spells: configuring Mage for a kernel

A **spell** is the configuration of one kernel mapped onto Mage. You describe
the mapping in Python (`spell.py`). Running it produces `spell.c`, which holds a
single C function, `mage_<kernel>_cfg()`, that programs the CGRA by writing its
memory-mapped configuration registers. Firmware calls that function, then
starts Mage.

This guide covers the DAE core (Mage) in detail. The streaming core (Rogue)
uses the same tool; its differences are summarised in
[Streaming (Rogue) spells](#streaming-rogue-spells).

## Quick start

```sh
# 1. Create the kernel directory, the builder and a spell.py scaffold
make spell-gen APP=vadd MAGE_CFG_HJSON=config/dae/cfg_4x4_4x2_full.hjson

# 2. Describe the mapping
$EDITOR sw/spells/dae/vadd/spell.py

# 3. Produce sw/spells/dae/vadd/spell.c (function mage_vadd_cfg)
make spell-run APP=vadd MAGE_CFG_HJSON=config/dae/cfg_4x4_4x2_full.hjson
```

Requirements: Python 3 with `hjson`, `mako` and `jsonref` (the same packages
`util/mage-gen.py` needs). Pass `PYTHON=/path/to/python` to `make` if they live
in a virtual environment.

## How the pieces fit

```
config/<dae|streaming>/<cfg>.hjson        the hardware instance
        │
        │  util/spell-gen.py  (renders Mako templates)
        ├──► MageSpellBuilder.py   builder class for exactly this hardware
        │                           (generated, not tracked by git)
        └──► spell.py              scaffold with every call pre-filled,
                    │               created once, then edited by you
                    │  python3 spell.py
                    ▼
                 spell.c           mage_<kernel>_cfg()
```

| File | Origin | Edit it? |
|---|---|---|
| `sw/spells/MageSpellBuilder.py.tpl` | template | Only to change how configurations are encoded |
| `sw/spells/spell.py.tpl` | template | Only to change the scaffold |
| `sw/spells/<arch>/<kernel>/MageSpellBuilder.py` | generated by `spell-gen` | No: regenerate instead |
| `sw/spells/<arch>/<kernel>/spell.py` | scaffold from `spell-gen`, then yours | Yes, this is the mapping |
| `sw/spells/<arch>/<kernel>/spell.c` | generated by `spell-run` | No |

Make targets:

| Target | What it does |
|---|---|
| `make spell-gen APP=<k> MAGE_CFG_HJSON=<cfg>` | Creates `sw/spells/<arch>/<k>/`, (re)generates `MageSpellBuilder.py`, and writes the `spell.py` scaffold **only if it does not exist yet** |
| `make spell-run APP=<k> MAGE_CFG_HJSON=<cfg>` | Runs `spell.py`, writing `spell.c` next to it |

`<arch>` (`dae` or `streaming`) is taken from the directory of
`MAGE_CFG_HJSON`. Override the kernel directory with `SPELL_DIR=...`.

Re-run `spell-gen` whenever the configuration or the builder template changes:
the builder is specific to one hardware instance, and a stale one encodes the
wrong layout.

You can also call the generator directly:

```sh
python3 util/spell-gen.py --mage_cfg <cfg.hjson> --outdir <dir> --tpl-sv sw/spells/MageSpellBuilder.py.tpl
python3 util/spell-gen.py --mage_cfg <cfg.hjson> --outdir <dir> --tpl-sv sw/spells/spell.py.tpl
```

## Choosing a configuration

A spell only works on the hardware instance it was generated for: the PE word
width, the number of AGEs, the input-mux encodings and the register offsets all
depend on the configuration. Use the **same HJSON file** that `make mage-gen`
used to generate the RTL you will run on.

DAE configurations are named `cfg_<rows>x<cols>_<streams>x<ages per stream>[_<...>]_<full|part>.hjson`:

- `full`: 32-bit datapath only.
- `part`: packed-SIMD datapath. Each PE takes a `vecMode` (32, 16 or 8 bits) and
  the general configuration takes an accumulation vector mode.
- A trailing `_2x1` (e.g. `cfg_3x2_2x2_2x1`) means extra streams with a single
  AGE each. The exact per-stream AGE counts are in `n_age_per_stream_ds`.

The fields of the configuration that matter when writing a spell:

| Field | Meaning for the spell |
|---|---|
| `n_pea_rows`, `n_pea_cols` | PE coordinates, `PE_<r>_<c>` |
| `n_age_per_stream_ds` | AGEs per stream; AGE `(stream, id)` pairs exist for `id < n_age_per_stream_ds[stream]` |
| `n_age_tot` | Total AGEs, which is also the number of memory banks and memory ports |
| `n_pe_in_mem` | Number of `MEM_IN_<i>` inputs per PE |
| `pea_in_mem_placement` | For PE row `r`, `MEM_IN_<i>` reads memory port `pea_in_mem_placement[r][i]` |
| `has_delay_pe` | PEs take an extra `delayOpSel` argument |

## The DAE data path, as a spell sees it

```
 banks ──► load crossbar ──► memory ports ──► PEA ──► row outputs ──► store crossbar ──► banks
   ▲        (per stream)       MEM_IN_<i>             (left/right)      (per stream)       ▲
   └─────────────── AGEs generate the bank addresses for loads and stores ─────────────────┘
                     driven by 4 nested hardware loops (HWLP)
```

Everything is indexed by a **flat port index** `s`, numbering AGEs stream by
stream. With `n_age_per_stream_ds = [2, 1, 2]`:

| Stream | AGE id | Flat index `s` (AGE, bank, memory port) |
|---|---|---|
| 0 | 0, 1 | 0, 1 |
| 1 | 0 | 2 |
| 2 | 0, 1 | 3, 4 |

- **Hardware loops** produce four induction variables (IVs). Loop 0 is the
  innermost one.
- **AGEs**: each AGE computes an address from the IVs, the strides and a
  constant, and either loads from or stores to its bank.
- **Load crossbar** (per stream): memory port `s` takes the data loaded by one
  of the AGEs of its own stream.
- **PEs** read memory ports through `MEM_IN_<i>`. For a PE in row `r`,
  `MEM_IN_<i>` is memory port `pea_in_mem_placement[r][i]`.
- **Row outputs**: each PE row has a left and a right output. Each output
  forwards the result of one PE column of that row. The left output of row `r`
  is output port `r`; the right output is output port `n_pea_rows + r`. Only
  ports below `n_age_tot` reach memory.
- **Store crossbar** (per stream): bank `s` is written with one of the output
  ports of its own stream.

## Writing a DAE spell

The scaffold contains one function per configuration section, each already
filled with every call it needs (set to "unused" values), plus a `main()` that
calls them in order and writes `spell.c`. Edit the values; leave `main()` as it
is unless you need a different output path or function name.

All bit-string constants below are defined at the top of the generated
`spell.py`. Values whose register field is zero are not written, because the
hardware reset value is already zero.

### Hardware loops: `defineHwlpConfiguration`

```python
mage.insertHwlpConfiguration(ilb, flb, li)   # three lists of 4 ints
```

- Index `i` of each list is **hardware loop `i`**, the same `i` used by `{i}` in
  AGE addresses. Loop 0 is the innermost loop.
- Loop `i` counts from `ilb[i]` to `flb[i]` **inclusive**, step `li[i]`:
  `N` iterations means `flb = N-1`.
- All values are 8-bit (0–255).
- Unused loops: `ilb = flb = li = 0`.

```python
# for j in 0..15:        (loop 1)
#   for i in 0..7:       (loop 0, innermost)
ilb = [0, 0, 0, 0]
flb = [7, 15, 0, 0]
li  = [1, 1, 0, 0]
```

### General configuration: `defineGeneralConfiguration`

```python
mage.insertGeneralConfiguration(ii, vecMode)
```

- `ii`: initiation interval, 4 bits (0 leaves the register untouched).
- `vecMode`: accumulation vector mode, `part` configurations only:
  `VEC_MODE_32_BIN`, `VEC_MODE_16_BIN` or `VEC_MODE_8_BIN`.

### PE operations: `definePeaConfigurations`

```python
# argument list depends on the configuration (see the prototype comment in spell.py)
mage.insertPeConfiguration(PE_r_c, input0, input1, operation)                        # full
mage.insertPeConfiguration(PE_r_c, input0, input1, operation, delayOpSel)            # full + has_delay_pe
mage.insertPeConfiguration(PE_r_c, input0, input1, operation, vecMode, delayOpSel)   # part + has_delay_pe
```

`input0` / `input1` select the operands:

| Constant | Operand |
|---|---|
| `CONSTANT` | The PE's constant register (see `definePeaConstants`) |
| `MEM_IN_<i>` | Memory port `pea_in_mem_placement[row][i]` |
| `UP`, `LEFT`, `RIGHT`, `DOWN` | Output of the neighbouring PE |
| `SELF` | This PE's own output (feedback) |
| `DELAY_OP` | The delayed operand chosen by `delayOpSel` |

`operation` (GEMM ISA, used by every current DAE configuration):

| Constant | Operation | Constant | Operation |
|---|---|---|---|
| `NOP` | no operation | `MAX` | maximum |
| `MUL` | multiply | `MIN` | minimum |
| `SUB` | subtract | `ABS` | absolute value |
| `LSH` | left shift | `ACC` | accumulate |
| `LRSH` | logical right shift | `ADD` | add |
| `ARSH` | arithmetic right shift | `FW_A` / `FW_B` | forward input A / B |

`vecMode` (`part` only) is the element width: `VEC_MODE_32`, `VEC_MODE_16` or
`VEC_MODE_8`. Note this takes the plain width constants, not the `_BIN` ones used
by `insertGeneralConfiguration`.

`delayOpSel` (`has_delay_pe` only) is `D_<DIR>_OP_<OPERAND>`: it takes, from the
neighbour in direction `<DIR>` (`UP`, `LEFT`, `RIGHT`, `DOWN`), its result
(`RES`), its input A (`A`), its input B (`B`) or nothing (`NONE`). Use
`D_UP_OP_NONE` when the PE doesn't use `DELAY_OP`.

### PE constants: `definePeaConstants`

```python
mage.insertPeConstant(PEA_ROW_r, PEA_COL_c, value)
```

`value` is a 32-bit integer, or a string that is copied verbatim into `spell.c`
(for example a C macro defined by the firmware: `"BIAS"`).

### Load crossbar: `defineLoadStreamConfigurations`

```python
mage.insertLoadStreamConfiguration(PE_GROUP_g, PE_ID_k, AGE_ID_a)
```

Memory port `k` of stream `g` receives the data loaded by AGE `a` of the same
stream.

### Store crossbar: `defineStoreStreamConfigurations`

```python
mage.insertStoreStreamConfiguration(BANK_GROUP_g, BANK_ID_k, PE_ID_p)
```

Bank `k` of stream `g` is written with output port `p` of the same stream
(stream-local index, i.e. flat output port `base(g) + p`).

### Row outputs: `defineSelOutPeaColConfigurations`

```python
mage.insertSelOutPeaColConfiguration(PEA_ROW_r_OUT_LEFT,  PEA_COL_c)   # output port r
mage.insertSelOutPeaColConfiguration(PEA_ROW_r_OUT_RIGHT, PEA_COL_c)   # output port n_pea_rows + r
```

Selects which column of row `r` feeds that output port. There is no "no output"
value in DAE mode: an output port's data only reaches memory when a store AGE
writes it, so leave unused outputs at `PEA_COL_0`.

To store the result of PE `(r, c)`:

1. Pick the output port: `s = r` (left) or `s = n_pea_rows + r` (right),
   with `s < n_age_tot`.
2. Select column `c` on it with `insertSelOutPeaColConfiguration`.
3. Route port `s` to a bank of the same stream with
   `insertStoreStreamConfiguration`.
4. Configure an active store AGE that addresses that bank.

### AGEs: `defineAguConfigurations`

```python
mage.insertAgeConfiguration(AGE_GROUP_g, AGE_ID_a,
                            loopSel, startBank, numBanks, blockSize,
                            loadNotStore, selIvConstraint, isAccStore, isActive,
                            array, strideModes=None, accHwlpSel=0)
```

| Argument | Bits | Meaning |
|---|---|---|
| `loopSel` | 4 | Hardware-loop register-file entry whose IVs drive this AGE |
| `startBank` | 2 | First bank of the access |
| `numBanks` | 2 | Bank interleaving: number of banks the array is spread over |
| `blockSize` | 2 | Bank interleaving: block size |
| `loadNotStore` | 1 | 1 = load, 0 = store |
| `selIvConstraint` | 3 | **4 = unconstrained.** 0–3: the AGE only issues on the iterations where that IV equals the IV-constraint value, see [IV constraints](#iv-constraints-defineivconstraints) |
| `isAccStore` | 1 | 1 = store of an accumulated result |
| `isActive` | 1 | 0 disables the AGE (its whole word is written as 0) |
| `array` | — | Address expression, see below |
| `strideModes` | 4×1 | Per-IV addressing mode, default `[0, 0, 0, 0]` |
| `accHwlpSel` | 4 | Hardware-loop register-file entry that sets the accumulation reset point when `isAccStore = 1` |

**Address expression.** `array` is a string such as

```python
"A[4*{1} + 1*{0} + 16]"
```

- `s*{i}` multiplies IV `i` by stride `s`. Each stride is bound to the IV named
  in its braces, so the order of the terms doesn't matter. IVs that don't
  appear get stride 0.
- The trailing number before `]` is the constant offset.
- Strides and the constant are unsigned 8-bit values. The array name is
  ignored.
- Inactive AGEs conventionally use `"Array[0*{0}+0*{1}+0*{2}+0*{3}+0]"`.

> **Set `selIvConstraint = 4` on every AGE that should issue on every
> iteration.** The scaffold fills in 0, which only does no harm while the AGE
> is inactive. An active AGE with `selIvConstraint = 0` and constraint 0 issues
> only on the iterations where IV 0 is 0.

For the bank-interleaving fields (`startBank`, `numBanks`, `blockSize`), see
the bank and address computation in `hw/mage/access/age.sv.tpl`.

**Stride modes.** For each IV `i`:

- `strideModes[i] = 0` (linear): term = `Si * iv_i`.
- `strideModes[i] = 1` (tiled): term = `(iv_i >> log2(Si)) * (iv_i % Si)`, with
  `Si` a power of two. In this mode the number you write in front of `{i}` is
  **`log2(Si)`** (0–7), not `Si`: write `"A[2*{0}+0]"` for `Si = 4`.

### IV constraints: `defineIvConstraints`

```python
mage.insertAgeIvConstraint(AGE_GROUP_g, AGE_ID_a, value)   # 8-bit
```

Sets the value compared against the IV that the AGE's `selIvConstraint`
selects (`hw/mage/access/hwlp_rou.sv`):

- `selIvConstraint = 4`: no constraint; `value` is ignored.
- `selIvConstraint = k` (0–3): the AGE issues only when IV `k` equals `value`
  **and** every IV below `k` is 0. For example, a store with `k = 1`,
  `value = 7` issues only when IV 1 is 7 and IV 0 is 0: once per complete
  pass of loops 0 and 1.
- For an accumulation store (`isAccStore = 1`) the constraint also defines when
  the accumulation ends, evaluated on the register-file entry chosen by
  `accHwlpSel`.

AGEs you never call this for get 0.

### Timing conventions

- A store AGE usually uses a later hardware-loop register-file entry than the
  loads it consumes (`loopSel`), to account for the PEA pipeline latency.
- When scaling a 32-bit mapping to 16- or 8-bit SIMD (`part` configurations),
  keep the strides of the 32-bit version and divide the loop bounds by 2 or 4.

## Walkthrough: the DAE example

`sw/spells/dae/example/spell.py` targets `cfg_4x4_4x2_full` (4×4 PEA, 4 streams
of 2 AGEs, `has_delay_pe`). It is a feature demo rather than a useful kernel:

```python
ilb, flb, li = [0, 0, 0, 0], [7, 0, 0, 0], [1, 0, 0, 0]       # loop 0: 8 iterations

mage.insertPeConfiguration(PE_0_0, MEM_IN_0, CONSTANT, ADD, D_UP_OP_NONE)
mage.insertPeConstant(PEA_ROW_0, PEA_COL_0, 5)                # PE(0,0) = mem port 0 + 5

mage.insertLoadStreamConfiguration(PE_GROUP_0, PE_ID_0, AGE_ID_0)       # port 0 ← AGE (0,0)
mage.insertSelOutPeaColConfiguration(PEA_ROW_0_OUT_LEFT, PEA_COL_0)     # output port 0 ← PE(0,0)
mage.insertStoreStreamConfiguration(BANK_GROUP_0, BANK_ID_1, PE_ID_0)   # bank 1 ← output port 0

# AGE (0,0): load A[i] on every iteration of loop 0 (selIvConstraint = 4)
mage.insertAgeConfiguration(AGE_GROUP_0, AGE_ID_0, 0, 0, 0, 0, 1, 4, 0, 1,
                            "Array[1*{0}+0*{1}+0*{2}+0*{3}+0]")
# AGE (0,1): accumulating store into bank 1; tiled mode on IV 0 (log2(Si) = 1)
mage.insertAgeConfiguration(AGE_GROUP_0, AGE_ID_1, 0, 0, 0, 0, 0, 0, 1, 1,
                            "Array[1*{0}+0*{1}+0*{2}+0*{3}+0]",
                            strideModes=[1, 0, 0, 0], accHwlpSel=3)
```

In this configuration `pea_in_mem_placement[0] = [0, 1, 4, 5]`, so `MEM_IN_0` of
row 0 is memory port 0. That port is fed by AGE (0,0), and PE(0,0) adds 5 to
each loaded value. Output port 0 (row 0, left) forwards PE(0,0), and the store
crossbar sends it to bank 1, which AGE (0,1) addresses.

AGE (0,1) is there to show the `strideModes` and `accHwlpSel` arguments; it is
not a meaningful store for this loop nest (it is an accumulation store
constrained on IV 0 = 0, and uses the same register-file entry as the load).
For a plain store, use `isAccStore = 0`, `selIvConstraint = 4` and a `loopSel`
that accounts for the PEA latency.

Resulting `spell.c` (excerpt):

```c
void mage_example_cfg(){
	mage_hwl_flb[0] = 0x00000007;   // FLB_0 = 7
	mage_hwl_li[0] = 0x00000001;    // INC_0 = 1
	mage_agu[0] = 0x80002040;       // AGE 0: valid, load, unconstrained
	mage_agu[1] = 0x80004000;       // AGE 1: valid, store, accumulation store
	mage_age_strides[0] = 0x1;
	mage_age_strides[1] = 0x1;
	mage_stride_mode[1] = 0x1;      // AGE 1: IV 0 tiled
	mage_acc_hwlp_sel[0] = 0x30;    // AGE 1: accHwlpSel = 3
	mage_pea_constants[0] = 0x5;
	mage_pea[0] = 0xa01;            // PE(0,0): ADD, MEM_IN_0, CONSTANT
	...
}
```

## Using spell.c in firmware

`spell.c` defines pointers to the configuration registers at file scope and one
function. It relies on the macros of the generated `sw/mage_x_heep.h` (which
includes `mage_regs.h` and X-HEEP's `core_v_mini_mcu.h`), so it must be built
against the headers generated from the **same** configuration:

```c
#include <stdint.h>
#include "mage_x_heep.h"
#include "mage.h"
#include "spell.c"            // or compile it separately with the same includes

int main(void) {
    // ... copy input data into the banks (START_MAGE_BANK_<k>) ...
    mage_vadd_cfg();
    mage_start();
    while (!is_mage_finished());
    // ... read results back from the banks ...
}
```

The function only writes the fields the spell sets to non-zero values. Run it on
a freshly reset Mage, or clear the configuration registers first when chaining
kernels.

## Streaming (Rogue) spells

Generate against a configuration in `config/streaming/`; the scaffold lands in
`sw/spells/streaming/<kernel>/`. The DAE-only sections (hardware loops, AGEs,
crossbars, IV constraints) are absent. The differences:

- **Inputs**: `STREAM_IN<i>` instead of `MEM_IN_<i>`, plus `RF` (the PE's local
  register file). `DELAY_OP` only exists with the activation ISA.
- **`insertPeConfiguration`** takes an extra `enRF` argument (5 bits, register
  file enables: an int or a binary string) before `delayOpSel`. In `part`
  configurations `vecMode` comes before `enRF`.
- **ISA**: the activation configurations use a larger opcode table (`DIV`,
  `REM`, `MAXS`, `SHACC`, `CMULADD`, `CLIP`, ...). Use the constants the
  scaffold defines for your configuration.
- **Outputs**: `insertSelOutPeaRowConfiguration("<col>", row)` selects which row
  of each column is streamed out; `NO_OUTPUT` (= `n_pea_rows`) disables it.
- **Accumulators**: `insertPeAccValue(row, col, value)` sets the reset value of
  a PE's accumulator.

The generated streaming `spell.c` compiles against the streaming headers for
every configuration in `config/streaming/`, but its register encodings have not
been checked as thoroughly as the DAE ones.
`sw/spells/streaming/example/spell.py` targets `cfg_s4x4_4x4_part`.

## Errors and troubleshooting

The builder refuses to write a value that doesn't fit its register field, since
that would silently shift the neighbouring fields. Typical messages:

| Message | Cause |
|---|---|
| `flb[1] = 300 does not fit in 8 bits` | Loop bounds, increments and initial values are 8-bit |
| `AGE (stream 0, id 1): every stride must fit in 8 bits` | A stride in `array` is above 255 |
| `... IV 0 is in tiled mode, so its stride field holds log2(Si) and must be in 0..7` | You wrote `Si` instead of `log2(Si)` for a tiled IV |
| `AGE (...): a configuration field exceeds its bit width` | `loopSel` > 15, `startBank`/`numBanks`/`blockSize` > 3, `selIvConstraint` > 7, the constant or IV constraint > 255 |
| `A[...]: IV {4} is out of range or repeated` | Only `{0}`–`{3}` exist, each at most once |
| `PE 01: configuration word is N bits, expected M` | A wrong-width string passed to `insertPeConfiguration` (use the scaffold's constants), or a builder generated for another configuration |
| `<cfg>: missing top-level 'has_delay_pe' field` | The configuration predates that field; add it |
| `KeyError: <n>` | A stream, row or column index that doesn't exist in this configuration |

Other things to check when the hardware doesn't do what the spell says:

- Every active AGE that should run on every iteration has `selIvConstraint = 4`.
- PE ids and in-stream indices are spelled correctly. A PE id that doesn't
  exist (e.g. `"44"` on a 4×4 array) or an AGE/port id past the end of its
  stream is **silently ignored**, not rejected.

- `MageSpellBuilder.py` was regenerated after the last configuration or template
  change (`make spell-gen` again).
- The firmware headers (`mage_regs.h`, `mage_x_heep.h`) were generated from the
  same configuration as the spell (`make mage-gen-sw MAGE_CFG_HJSON=...`).
- Loop lists are indexed by loop number, innermost first. Spells written for the
  old Mage-Utils generator listed them in the opposite order.

## Keeping the generator in sync with the RTL

`MageSpellBuilder.py.tpl` and `spell.py.tpl` hand-encode layouts defined in the
RTL templates. When one of these changes, update the spell templates to match:

| RTL source | What the spell templates mirror |
|---|---|
| `hw/mage/configuration/mage_regs.hjson.tpl` | Register names, multireg counts, field positions |
| `hw/mage/configuration/peripheral_regs.sv.tpl` | Width and order of the crossbar and output-select fields |
| `hw/mage/packages/agu_pkg.sv.tpl` | `*_LSB`/`*_MSB` of the AGE word (not the order of `stream_inst_t`) |
| `hw/mage/packages/pea_pkg.sv.tpl` | PE word layout, opcodes, input-mux and delay encodings |
| `hw/mage/execute/pea.sv.tpl` | Output port to row mapping, `pea_in_mem_placement` |
| `sw/mage_x_heep.h.tpl` | `*_START_ADDR` macros used by `spell.c` |
